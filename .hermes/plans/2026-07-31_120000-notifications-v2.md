# Notification System v2 — Implementation Plan

> **For Hermes:** Implement this plan task-by-task on a feature branch; Greptile review against master before merge (per Henry's workflow).

**Goal:** Replace the current TFE-style webhook notification configs with a full event → rule → destination → template notification system, delivered via Apprise (100+ services), with first-class UI for a handful of services plus an "Apprise (Custom)" escape hatch.

**Architecture:** Org-scoped entities (`notification_destinations`, `notification_rules`, `notification_templates`, `notification_deliveries`) replace the workspace-scoped `notification_configurations`. The worker/routes emit typed events (`workspace.run.started`, `workspace.apply.failed`, …); a matcher evaluates rules (event type + workspace tag filters) against each event's context; matching rules render a template (mustache-style `{{var}}` substitution) and hand the rendered message + destination to the Apprise CLI (Python, pip-installed into the image), which does the actual delivery. Every attempt is logged to `notification_deliveries` with success/failure + response body.

**Tech Stack:** Bun/Elysia (unchanged), Drizzle + SQLite (unchanged), Python `apprise` CLI (new runtime dep, delivered in Docker image), React 19 + shadcn/ui (unchanged).

## Key Decisions (assumptions — flag if wrong)

1. **Org-scoped, not workspace-scoped.** Destinations/rules/templates live at org level (matches Henry's "Production Alerts" example — one destination, many workspaces). Rules carry workspace filters (tags) instead of a workspace FK.
2. **Apprise is the single delivery engine.** Even Slack/Discord/SendGrid UI entries get compiled into an Apprise URL internally; the "Custom" type stores a raw Apprise URL string. One code path for delivery, 100+ services for free.
3. **Drop the old table + code.** No migration shim, no wire-compat with TFE's notification-configurations API (clean-room; Henry said rip it out). Old endpoints removed; frontend section replaced.
4. **Events are strings with a context object** (`{ workspace: {name, id, tags}, run: {...}, ... }`), not per-event payload types. Templates reference context via `{{workspace.name}}` etc. Keeps the model extensible.
5. **Templates are org-level, with sensible defaults seeded per event type.** Rules reference a template; a "default" (null template) falls back to the seeded default for that event.
6. **Deliveries are logged** (destination, rule, event, workspace, status, error, attempts, timestamps) — needed for the UI history view and debugging.

## Apprise Integration

- Install: `apt-get install -y python3 python3-pip && pip3 install apprise` in Dockerfile (builder stage copies nothing; runtime image gets it directly). Also on host for tests: `pip3 install apprise` (or venv + symlink).
- Invocation (per delivery, from `lib/notify.ts`):
  ```bash
  apprise --body=<rendered body> --title=<rendered title> --config=<temp apprise.yml> --notification-type=info|success|warning|failure
  ```
- Generated config file (per destination, written to a temp dir under STORAGE_DIR, mode 0600):
  ```yaml
  urls:
    - <apprise url for the destination>
  ```
- URL compilation per destination type:
  - `slack` → `slack://xoxb-<token>/<channel>` (incoming-webhook variant if user pastes a webhook URL: detect `hooks.slack.com` → use `slack://` webhook form if supported, else pass through)
  - `discord` → `discord://<webhook_id>/<webhook_token>/`
  - `sendgrid` → `sendgrid:///<api_key>:<from_email>/<to_email>`
  - `apprise-custom` → the raw string the user entered (validated with `apprise --dry-run`-style check or schema parsing at save time)
- Notification type mapping from event: failure events → `failure`, completed → `success`, others → `info`.
- Timeout: `--timeout=10` (CLI flag) or `AbortSignal.timeout` on the subprocess. Exit code 0 = delivered.
- Validation at save time: run `apprise --dry-run --config=<temp>` (or parse via `python -c "import apprise; ..."`) to reject malformed URLs. Keep it simple: basic scheme prefix validation in TS + dry-run in a test endpoint.

export const notificationDestinations = sqliteTable("notification_destinations", {
  id: text("id").primaryKey(),
  orgId: text("org_id").notNull().references(() => organizations.id, { onDelete: "cascade" }),
  name: text("name").notNull(),
  type: text("type").notNull(),            // 'slack' | 'discord' | 'sendgrid' | 'apprise-custom'
  config: text("config", { mode: "json" }).$type<Record<string, string>>().notNull(),  // type-specific fields
  enabled: integer("enabled", { mode: "boolean" }).notNull().default(true),
  createdAt: integer("created_at").notNull().$defaultFn(() => Date.now()),
});

export const notificationTemplates = sqliteTable("notification_templates", {
  id: text("id").primaryKey(),
  orgId: text("org_id").notNull().references(() => organizations.id, { onDelete: "cascade" }),
  name: text("name").notNull(),
  eventType: text("event_type").notNull(), // which event this template is for
  titleTemplate: text("title_template").notNull(),
  bodyTemplate: text("body_template").notNull(),
  createdAt: integer("created_at").notNull().$defaultFn(() => Date.now()),
});

export const notificationRules = sqliteTable("notification_rules", {
  id: text("id").primaryKey(),
  orgId: text("org_id").notNull().references(() => organizations.id, { onDelete: "cascade" }),
  name: text("name").notNull(),
  eventType: text("event_type").notNull(),
  workspaceTagFilters: text("workspace_tag_filters", { mode: "json" }).$type<{ key: string; value: string }[]>().notNull().default([]),
  destinationId: text("destination_id").notNull().references(() => notificationDestinations.id, { onDelete: "cascade" }),
  templateId: text("template_id").references(() => notificationTemplates.id, { onDelete: "set null" }), // null = default template for event
  enabled: integer("enabled", { mode: "boolean" }).notNull().default(true),
  createdAt: integer("created_at").notNull().$defaultFn(() => Date.now()),
});

export const notificationDeliveries = sqliteTable("notification_deliveries", {
  id: text("id").primaryKey(),
  orgId: text("org_id").notNull(),
  ruleId: text("rule_id").references(() => notificationRules.id, { onDelete: "set null" }),
  destinationId: text("destination_id").notNull(),
  workspaceId: text("workspace_id").references(() => workspaces.id, { onDelete: "set null" }),
  eventType: text("event_type").notNull(),
  title: text("title"),
  body: text("body").notNull(),
  successful: integer("successful", { mode: "boolean" }).notNull(),
  error: text("error"),
  attempts: integer("attempts").notNull().default(1),
  createdAt: integer("created_at").notNull().$defaultFn(() => Date.now()),
});

## Risks / Tradeoffs / Open Questions

1. **Apprise is Python** — adds python3 (~50MB) to the image and a subprocess hop. Alternative: hand-rolled HTTP for the 4 supported types + apprise only for custom (defeats "generate the Apprise config behind the scenes"). Decision: accept Python dep — Henry explicitly wants Apprise as the engine.
2. **Slack auth variants** — apprise `slack://` supports both bot-token and incoming-webhook forms; UI should offer both or auto-detect from pasted URL. Confirm exact schema at implementation time from `apprise --schemas`.
3. **Workspace tags** — need to confirm `workspaces` has a `tags` column; if not, add one (json) — TFE workspaces have tags, and Henry's example rule uses `workspace.tag.environment`.
4. **Notification type mapping** — failure→failure, completed→success, rest→info; simple and sensible, refine later.
5. **Email** — SendGrid via apprise's `sendgrid://` schema (API key + from + to). SMTP not in scope.
6. **Rate limits** — deliveries are async fire-and-forget; if a destination misbehaves we log failures and move on. No retry queue in v1 (apprise has internal retry; we cap subprocess timeout).
7. **Secrets** — destination configs (tokens/webhook URLs) stored plaintext in DB like the rest of Terrence (consistent with existing `token` column); masked in API responses (`token: null` pattern already used).
